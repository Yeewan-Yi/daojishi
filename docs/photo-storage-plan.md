# 有期：大量照片的长期存放方案

规划日期：2026-10-22。目标是两个人持续多年记录回忆，而不是把网站扩成公共图床。

## 推荐架构

**GitHub 放程序，Supabase 放回忆与索引，私有 R2 放网页图片，个人相册保留原图。**

| 层 | 保存什么 | 不保存什么 |
| --- | --- | --- |
| GitHub / Pages | 网页代码、字体、公开地图、程序化模型 | 私人照片、私有导出、服务端密钥 |
| Supabase Postgres | 两个人的访问权限、书信/游记、城市归属、照片说明、日期、存储商和对象标识 | 图片 Base64、图片二进制 |
| 私有 R2 Standard | 网页缩略图和查看版照片 | 默认不重复保存手机原图与长视频 |
| 私有相册 / 本地磁盘 | 完整原图、视频、原始 EXIF、批量备份 | 不以浏览器缓存充当备份 |

现在 Supabase 的私有图片仍可继续使用。本轮没有开通 R2 或搬动现有照片。若确定将集中上传上千张照片，建议在相册批量上传功能上线前完成 R2 接入，避免先上传后再大规模搬家。

官方配额与当前占用见 [总容量规划](storage-plan.md)。

## 一张照片保存哪些版本

1. **缩略图**：长边约 400 像素，目标 20–50 KB。城市回忆列表只读取这一版。
2. **查看版**：长边 1600–2048 像素，目标 200–500 KB。点击照片时才下载这一版；文字截图以可读性优先。
3. **原图**：保留在你们的私有相册和备份盘。照片详细页可记录原图档案号，不把个人云盘凭证或公开分享链接写入网页。

当前接口只接受 JPEG，第一阶段的缩略图和查看版可继续用 JPEG，兼容现有图片验证。以后若使用 WebP/AVIF，需同步增加服务端 MIME、文件头和尺寸校验，不能只更改文件后缀。

网页查看版去掉 GPS 等不需要的 EXIF；实际拍摄时间、地点由你们确认后作为私有回忆字段保存。当前压缩实现已经通过浏览器画布重新编码；这份方案没有重新压缩历史照片。

## 容量估算

以下按每张查看版 300 KB + 缩略图 30 KB、十进制计量，不包含原图、视频、请求费用或备份副本：

| 照片数量 | 网页图片总量 |
| ---: | ---: |
| 1,000 张 | 约 0.33 GB |
| 10,000 张 | 约 3.3 GB |
| 30,000 张 | 约 9.9 GB |

按核对当日官方定价，R2 Standard 免费层提供 10 GB-month 存储、每月 100 万 Class A 操作、1,000 万 Class B 操作，互联网出站流量免费。图片还会产生读取/写入操作，签名与鉴权服务也可能有自己的费用，不能把免费层理解为永久零成本。

建议 R2 达到 5 GB 时核对增速，达到 7 GB 时决定是否付费扩容或归档，而不等到配额用完。若每张手机原图为 8 MB，10,000 张便约 80 GB，因此“原图与网页浏览版分开保存”比更换数据库更有效。

## 上传和读取路径

未来相册使用 **鉴权后直传对象存储**，避免每一张照片都穿过 Supabase Edge Function 作为大文件中转：

1. 浏览器在本地生成缩略图和查看版。
2. 浏览器带现有房间与个人身份向服务端申请上传。服务端校验身份、单张大小、剩余预算和频率，并分配随机 `media_id`。
3. 服务端生成只允许向指定对象位置上传、短时有效的地址。浏览器直接把两个版本上传到私有 R2。
4. 上传完成后，服务端核实对象实际存在、大小和格式；完成校验才把照片标为可展示。不能仅相信客户端声明的文件大小、哈希或完成状态。
5. 浏览照片时，服务端再次校验当前房间身份，返回短时有效的读取地址；图片从 R2 直接送到浏览器。普通回忆查询只返回文字和图片元数据。
6. 私有桶不开匿名读取；CORS 仅用于限制正常浏览器来源，不能代替访问校验。临时签名地址是有时限的访问凭证，不当作永久公开链接保存。

R2 的服务端访问密钥只存 Secrets。前端只拿本次操作必需的临时地址，不拿管理员或对象存储密钥。

## 对象命名和数据结构

对象路径使用随机 ID，不把姓名、城市、纪念日或正文塞进路径：

```text
couples/{room_id}/media/{media_id}/thumb-v1.jpg
couples/{room_id}/media/{media_id}/view-v1.jpg
```

未来媒体索引应包含：`id`、`room_id`、`author_id`、`provider`、`object_key`、`variant`、`mime`、`bytes`、`width`、`height`、`sha256`、`status`、`created_at`。城市、游记和书信通过稳定的 `media_id` 引用照片，不直接绑定某个存储商的临时 URL。

预留 `reserved → uploaded → ready` 的上传状态，以及归档/删除状态，处理“上传成功但保存回忆失败”的情况。对象存储与数据库不是一个事务，必须可重试并避免重复计数。

同一张照片重复选择时，只在同一个房间内去重。相同照片可以同时被多封信、多个城市回忆引用；删除一个引用不能直接删除仍被其他回忆使用的对象。

## 页面如何避免大量下载

- 城市页每次读取约 20 条回忆，用游标分页；不一次加载整座城市的全部照片。
- 列表只显示缩略图，点击后取查看版；原图不随页面下载。
- 合并一页图片的签名请求，利用已鉴权图片的浏览器缓存。签名过期只重签必要资源。
- 实时同步传“有更新”和元数据版本，不在消息里传图片文件。
- 本地草稿缓存、浏览器图片缓存只是加速层；换电脑后仍应从共享数据恢复正式回忆。

## 从现有 Supabase 图片迁移

现有照片数量很少，无需急迁。未来接入时按以下顺序迁移：

1. 为新照片启用存储商字段和读取适配，旧照片仍从 Supabase 读取。
2. 将旧照片复制到私有 R2，核对字节数与哈希，不改变原有照片 ID 和回忆引用。
3. 用双方各自的身份验证查看权限、缩略图、历史分页和正文引用。
4. 再切换旧照片的存储索引，保留短期回退方案。
5. 检查独立备份可恢复后，再按明确的保留策略清理旧存储副本。

期间不更换你们的共享倒计时链接，也不把历史回忆重建成公开网页。

## 备份和清理

数据库导出不包含 Storage/R2 照片对象。需要分别备份：

- 回忆正文、城市关联和媒体索引的私有导出；
- 网页图片文件与校验清单；
- 原图相册。

至少保留主存储之外的一份私有备份，并定期抽查恢复。代码仓库只保留备份工具和结构说明，不保留私人备份文件。

照片可以进入回收站并设定明确保留期；正式清理前确认没有其他回忆引用。旧草稿需要先有服务端保留标记，才可安全清理其未使用附件。不会因为空间不足而自动删除正式回忆。

## 实施顺序

1. 现在：继续使用现有私有存储与压缩，保留原图个人备份。
2. 在大量上传前：接入私有 R2、缩略图、直接上传/读取、媒体索引适配和用量预算。
3. 再上线批量上传、城市相册与去重。
4. 完成迁移与独立恢复验证后，清理重复的旧存储副本。

本文件是未来实施方案；R2、缩略图、去重、批量相册、自动备份和告警尚未作为本轮功能上线。
