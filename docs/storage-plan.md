# 有期：二人网站的数据、代码与容量规划

核对日期：2026-10-22。适用于目前只有两位使用者的情侣网站。

## 结论

继续使用 GitHub Pages 承载网页和公开静态资源，Supabase 保存双人共享数据与压缩图片。现在无需升级套餐，也无需搬迁。把图片和带宽作为主要预算；照片增多后优先迁移图片存储，保留现有倒计时、传书和个人链接。

本文件是规划，不会自动开通付费服务、迁移或删除现有数据，也没有创建定期执行的任务。

## 已核实的现状

本次只读取聚合数字，没有读取书信正文或下载私人图片。

| 项目 | SQL 快照 | 说明 |
| --- | ---: | --- |
| 数据库 | 11,450,035 bytes，约 11.45 MB | `pg_database_size`，包含数据库内部对象，不等同于应用文字净大小；账单和额度以 Dashboard Usage 为准 |
| 未删除书信 | 12 封 | 用于规模估算 |
| 私有图片 | 1 张，351,195 bytes，约 0.35 MB | 由 `storage.objects` 元数据聚合 |
| 当月流量、函数调用量 | 未读取 | 不能将其视为 0；需要在 Dashboard Usage 查看 |
| 代码、字体、地图 | GitHub 仓库 / Pages | 不占 Supabase 数据库或 Storage；本次精细国界文件约 2.1 MB |

当前已具备：图片在浏览器中缩至最长边 1600 像素，压成 JPEG，每张上限 1.2 MB，每封最多 3 张；私有存储桶、个人身份校验、1 小时签名 URL、约 50 分钟的页面内 URL 缓存、图片懒加载。数据库只保存图片标识及尺寸等元数据，不存 Base64。

## 免费额度的含义

按核对当日官方价格页：

| 资源 | Free 配额 | 本站的使用原则 |
| --- | --- | --- |
| 数据库 | 500 MB | 保存文字、设置、人物身份和图片元数据 |
| 文件存储 | 1 GB | 仅保存网页使用的压缩照片 |
| Egress | 5 GB / 月 | 数据库 / 函数 / 非缓存资源的出站传输需计入相应额度 |
| Cached Egress | 另有 5 GB / 月 | 独立预算，不把两种流量简单当成可互换的 10 GB |
| Edge Functions | 500,000 次 / 月 | 上传、签名读取等功能消耗调用；普通数据库轮询不是每次都算 Edge 调用 |
| Realtime | 200 万消息 / 月，200 峰值连接 | 目前传书主要使用版本探测轮询，不能按已接入 Realtime 估算 |

Free 不提供可依赖的自动数据库备份；项目闲置一周可能暂停。临近额度应提前处理，不把免费额度当作无限制或可保证的服务能力。

来源：[Supabase Pricing](https://supabase.com/pricing)、[数据库备份](https://supabase.com/docs/guides/platform/backups)。

## 数据放在哪里

| 数据 | 主要位置 | 备份 / 扩容位置 |
| --- | --- | --- |
| HTML、JS、CSS、程序化 3D 模型、公开地图与字体 | GitHub 仓库 + GitHub Pages | Git 历史 + 本地仓库 |
| 倒计时起止时间、房间权限、两个人的身份、传书正文 | Supabase Postgres | 私有本地加密导出；未来可备份到个人私有云盘 |
| 履痕中的公共地理底图 | GitHub Pages | 和代码一起版本管理 |
| 南京、绍兴这类已确认城市的初始化列表 | 目前随前端发布 | 如果以后支持自行增删，改为房间范围的数据库记录；不把私人游记写进公开源码 |
| 私人照片的网页版本 | Supabase 私有 Storage | 图片增长后可迁入私有 Cloudflare R2 |
| 原图、长视频、完整相册 | 个人本地磁盘 / 私有相册存档 | 第二份个人私有备份；网站只保留浏览版本和受控引用 |
| 服务端密钥、对象存储凭证 | Edge Functions Secrets | 密钥管理器；不提交 Git，也不放进前端配置 |
| 临时草稿 | 当前浏览器 localStorage + 已上传的私有附件 | 这是草稿缓存，不能代替正式共享或备份 |

GitHub Pages 的站点文件公开可访问，不能用它承载私人相册或数据库导出。GitHub 官方目前规定发布站点不超过 1 GB，月带宽软限制 100 GB；本站的静态资源规模距此很远，但也不把 Git 仓库作为相册硬盘。

来源：[GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)。

## 建议的容量预算

以下是提前处理阈值，不是 Supabase 已设置的硬限额，也不是当前已经上线的拦截功能。

| 资源 | 关注线 | 处理线 | 建议动作 |
| --- | ---: | ---: | --- |
| 数据库 | 250 MB | 350 MB | 检查占比大的表和索引，归档不再使用的技术记录；保留有效回忆 |
| 图片存储 | 500 MB | 700 MB | 核对增长速度；准备把媒体迁移到 R2，保留约 30% 存储余量 |
| 非缓存出站流量 | 3 GB / 月 | 4 GB / 月 | 优先检查重复图片下载、完整历史重复拉取、失败重试 |
| 缓存出站流量 | 3 GB / 月 | 4 GB / 月 | 单独检查图片缓存命中及资源大小 |
| Edge 调用 | 300,000 / 月 | 400,000 / 月 | 检查 URL 签名是否重复调用、错误重试是否退避 |

每月人工查看 Usage；旅行集中上传前再看一次。若以后需要自动提醒，可再接只读用量检查，提醒只发给网站所有者，不向对方或公开页面暴露用量和个人链接。

## 图片增长的估算

按未来网页图片平均 **250 KB**、每天为两人合计数量、不含视频和其他流量估算：

| 每天新增图片 | 一年新增存储 |
| ---: | ---: |
| 1 张 | 约 91 MB |
| 5 张 | 约 456 MB |
| 10 张 | 约 913 MB |

因此，二人网站的文字一般不是最先触及限制的部分，持续增加的照片更值得预算。当前每张 1.2 MB 是硬上限，不代表平均大小会是 250 KB；如果每张都接近上限，约 580 张便会达到 700 MB 处理线。

建议的后续图片策略：

1. 正文列表用 320–480 像素、约 20–50 KB 的缩略图；点开后才加载 1600 像素的查看版。生成缩略图后只由服务端验证身份并返回私有签名地址。
2. 查看版以 150–400 KB 为目标；文字截图允许更大的体积来保证可读性。这里是建议目标，当前压缩上限未在本次修改中改变。
3. 不把原图和查看版重复塞进免费 Storage；原图保存在个人相册。网页照片保留与原图对应的稳定标识，方便未来重建。
4. 上传后计算哈希，未来在同一房间内去重，避免相同图片被反复保存。不得跨房间暴露哈希或文件存在性。
5. 当前签名 URL 和 `cacheControl: 3600` 已可减少重复读取；但页面刷新后的重新签名与浏览器缓存行为仍需观察。不能把签名 URL 缓存当作图片完全不消耗流量。

## 代码和请求的节流

- 地图、字体和 3D 模型继续由 Pages 提供，不绕经 Supabase。
- 页面倒计时在浏览器本地计算，不能为每秒或每位小数向后端请求。
- 倒计时和传书目前有小体积版本探测；有变化时才取内容，历史分页继续保留。
- 当前隐藏页面仍有约 15 秒轮询。后续若长期常驻，优先改为更低频的后台检查或身份受控的 Realtime + 断线补查；先测量实际带宽，再决定，不因功能增加就同时叠加两种高频同步。
- 退避失败重试，签名请求合并，缩略图懒加载；避免打开一次履痕就下载全部历史相册。
- 技术日志设定保留期限，正文回忆不按时间自动删。

## 达到处理线后的扩容顺序

**优先迁媒体，保留 Supabase 数据与访问校验。**

当照片接近 700 MB，或按增长速度预计六个月内触及上限时，考虑私有 R2 存储。核对当日 R2 Standard 免费层为 10 GB-month、100 万 Class A 操作和 1,000 万 Class B 操作，互联网出站流量免费；不是无限存储或无限请求，Workers、其他服务及超额部分需另行预算。

迁移时保留原有房间与个人身份校验，服务端签发有时限的 R2 地址。数据库保存 `provider`、`object_key`、大小、哈希和版本，不写死临时签名 URL。迁移要先复制、比对哈希、验证双方访问，再切换引用；原存储只在核实备份和访问后清理。

[Cloudflare R2 Pricing](https://developers.cloudflare.com/r2/pricing/)

如果后续是数据库、持续可用性或运维能力超过免费层，而不仅是照片增加，再考虑 Supabase Pro。核对当日起价为 $25 / 月，不能把这项费用当作当前已产生的账单。

目前没有开通 R2、没有升级套餐，也没有改变你现有的数据位置。

## 备份与清理

- 正式启用后，建议每月以及每次大批上传后各做一次私有备份；目前没有配置自动备份任务。
- 数据库导出与照片文件分别备份：数据库备份只包含 Storage 元数据，不包含照片本身。
- 备份建议放在 Git 仓库以外的私有目录，并保留第二份个人私有备份；导出包含房间能力令牌和身份数据时需加密。
- 每季度抽查一次恢复：设置、书信、城市引用和图片可打开，才算备份有效。
- 本站删除书信采用软删除，图片不会因为正文隐藏就必然释放空间。以后需要统计已删记录的引用，再提供可恢复的回收站和明确的保留期。
- 当前图片草稿仅在浏览器记录，服务端无法准确判断一个旧附件是否仍被草稿需要。因此现在不按“上传时间太久”自动清理照片。将来先增加服务端草稿保留标记，再实现过期、未引用附件的清理。
- 正式回忆不因额度接近上限而自动删除。

## 本轮已做与后续规划的界限

已做：核对官方额度、只读统计当前占用、梳理现有压缩与访问缓存、继续把更细的地图保存在 GitHub，并修正履痕交互。

后续规划：缩略图、按房间去重、用量告警、私有导出与恢复工具、媒体迁移适配。没有将这些规划表述为已经上线的功能。
